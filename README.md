# Proxy Stack Installer

Автоматическая установка собственного прокси-стека на чистый VPS с Ubuntu или Debian.

Один Bash-скрипт разворачивает два варианта MTProto, экспериментальный Telegram WEB Proxy, SOCKS5 и VLESS WebSocket+TLS. IPv6 включается только при передаче отдельного IPv6-домена.

> Используйте проект только на серверах, которыми вы имеете право управлять, и соблюдайте применимое законодательство и правила хостинг-провайдера.

## Что устанавливается

| Сервис | Порт | IPv4 | IPv6 | Назначение |
|---|---:|:---:|:---:|---|
| MTProto FakeTLS (MTG) | TCP/443 | Да | Опционально | Основной прокси Telegram |
| Telegram WEB Proxy | HTTPS/443 | Да | Нет | WebView-транспорт через `tproxy-server` |
| MTProto legacy random padding | TCP/8443 | Да | Опционально | Резервный прокси Telegram |
| SOCKS5 с логином и паролем | TCP/1080 | Да | Опционально | Универсальный TCP-прокси |
| VLESS WebSocket+TLS | TCP/443, TCP/9443 | Да | Опционально | Happ и другие VLESS-клиенты; `443` основной, `9443` резервный |
| HTTP ACME challenge | TCP/80 | Да | Опционально | Выпуск и продление сертификата Let's Encrypt |

Дополнительно устанавливаются:

- nginx как TLS-терминатор и WebSocket reverse proxy;
- [MTG 2.3.0](https://github.com/9seconds/mtg/releases/tag/v2.3.0) с проверкой SHA-256 — реализация MTProto FakeTLS, которая принимает Telegram и передаёт обычный TLS в nginx;
- официальный proof-of-concept `telegramdesktop/tproxy-server`, собранный из закреплённого коммита;
- Xray с закреплённой версией и проверкой SHA-256;
- UFW с открытием только необходимых публичных портов;
- автоматическое продление сертификата;
- ежедневное обновление relay-конфигурации Telegram;
- готовая Happ-подписка с VLESS-узлами.

## Требования

- чистый VPS на Ubuntu 22.04+ или Debian 12+ с `systemd`;
- архитектура `x86_64`;
- доступ `root` или `sudo`;
- свободные публичные TCP-порты `80`, `443`, `1080`, `8443` и `9443`;
- свободные локальные TCP-порты `8080` и `8081` для WEB relay;
- DNS-записи без Cloudflare/CDN-проксирования;
- первый домен только для IPv4;
- второй домен только для IPv6, если IPv6 нужен.

Публичный IPv4 должен быть назначен интерфейсу VPS: MTG привязывается к нему явно.
Скрипт не назначает IPv6-адрес сетевому интерфейсу: IPv6 должен быть заранее выдан
хостером и добавлен в систему. Установщик проверит, что AAAA-запись второго домена
указывает на реально назначенный VPS адрес. VPS за NAT без назначенного публичного
IPv4 этим сценарием не поддерживается.

## Подготовка DNS

### Только IPv4

Создайте одну A-запись:

```text
d1.example.com  A  203.0.113.10
```

У `d1.example.com` не должно быть AAAA-записи.

### IPv4 и IPv6

Используйте два разных домена:

```text
d1.example.com  A     203.0.113.10
d2.example.com  AAAA  2001:db8::10
```

- у первого домена не должно быть AAAA-записи;
- у второго домена не должно быть A-записи;
- IPv6-адрес должен быть назначен одному из интерфейсов VPS.

Проверить DNS можно командами:

```bash
dig +short A d1.example.com
dig +short AAAA d1.example.com
dig +short A d2.example.com
dig +short AAAA d2.example.com
```

## Установка

Склонируйте репозиторий на VPS и перейдите в его каталог:

```bash
git clone https://github.com/articks/proxy-stack-installer.git
cd proxy-stack-installer
```

### Только IPv4

```bash
sudo bash install-proxy-stack.sh d1.example.com
```

### IPv4 и IPv6

```bash
sudo bash install-proxy-stack.sh d1.example.com d2.example.com
```

Установщик проверит ОС, DNS, занятые порты, сертификат и доступность всех созданных сервисов. При ошибке выполнение остановится с диагностическим сообщением.

На `443` запускается MTG; имя службы `teleproxy.service` сохранено для совместимости
с командами администрирования. При втором домене создаётся отдельная
`teleproxy-ipv6.service`: MTG проверяет домен внутри EE-секрета, поэтому один
экземпляр не подходит сразу для двух разных доменов. IPv4 и IPv6 слушают только
свои публичные адреса, статистика — только loopback (`8888` и `8890`). Если второго
домена нет, IPv6-конфигурация и служба MTG не создаются.

## Результат

После успешной установки все клиентские параметры сохраняются в:

```text
/root/proxy-credentials.txt
```

Файл содержит:

- MTProto FakeTLS через домен и IP;
- MTProto legacy через домен и IP;
- Telegram WEB Proxy через основной IPv4-домен;
- SOCKS5 через домен и IP;
- VLESS URI через домен и IP;
- отдельные IPv6-конфигурации, если передан второй домен;
- URL готовой Happ-подписки;
- команды диагностики.

Показывайте файл только доверенным пользователям: в нём находятся все секреты доступа.

## Telegram WEB Proxy

WEB Proxy использует только имя хоста и MTProto-секрет. Внешний HTTPS-порт
зафиксирован протоколом на `443`, поэтому произвольный публичный порт указать
нельзя. Установщик сохраняет существующий MTProto FakeTLS на том же порту и
добавляет отдельный relay на локальных адресах `127.0.0.1:8080` и
`127.0.0.1:8081` по цепочке:

```text
Telegram -> HTTPS/443 -> MTG -> nginx -> tproxy-server -> MTProxy
```

Готовые `Hostname`, `Secret` и `tg://webproxy`-ссылка записываются в
`/root/proxy-credentials.txt`. WEB Proxy настраивается только для первого,
IPv4-домена; подключение по IP не поддерживается из-за TLS и привязки
производного bridge-ключа к имени хоста.

MTG не заменяет WEB relay: `tproxy-server` продолжает работать с официальным
MTProxy на `8443`. При переходе существующей установки на MTG прежний WEB-секрет
и ссылка сохраняются. Один секрет может использоваться несколькими клиентами
одновременно; MTProto и WEB Proxy также могут работать параллельно.

На момент фиксации этой версии upstream называет реализацию
[proof-of-concept](https://github.com/telegramdesktop/tproxy-server): Desktop-клиент
реализован, Android экспериментален, а iOS описан как план. Обычные клиенты без
пункта `WEB Proxy` этот вариант использовать не смогут.

## Happ

Скопируйте URL подписки из `/root/proxy-credentials.txt` и добавьте его в Happ. Подписка включает:

```text
#proxy-enable: 1
#fragmentation-enable: 0
```

Подписка содержит два IPv4-узла: основной `443` и резервный `9443`. При наличии
второго домена добавляются ещё два IPv6-узла с теми же портами.
Новые установки используют TLS fingerprint `edge`. Он выбран после сквозной
проверки в Happ: вариант `safari` на проверяемом подключении зависал при TLS,
а с `edge` работали запросы, скачивание и отправка данных. Проверка сертификата
и имени домена остаётся включённой; `allowInsecure` не используется.
Это настройка совместимости, а не гарантия доступности через любого провайдера.

Основной VLESS-маршрут делит внешний `443` с MTProto и WEB Proxy: MTG
передаёт обычный TLS во внутренний nginx, а nginx выбирает Xray только по
точному секретному WebSocket-пути. Порт `9443` остаётся доступным как резервный.

Установщик создаёт один файл подписки с одним идентификатором. Он не добавляет
старые Reality/TUN-профили и не объединяет найденные на сервере подписки.

Если профиль был добавлен вручную отдельной VLESS-ссылкой, обновление файла
подписки его не изменит. В старых ручных профилях при таком TLS-тайм-ауте замените
только `fp=safari` на `fp=edge` (в редакторе Happ — TLS Fingerprint: `safari` →
`edge`), сохраните и переподключитесь. UUID, SNI, Host, путь и проверку
сертификата менять не нужно. Либо импортируйте подписку из файла доступов.

Не включайте одновременно встроенный MTProto/SOCKS5-прокси Telegram и системный прокси Happ: двойное проксирование может вызвать лавину повторных соединений.

## Повторный запуск

Сгенерированные секреты хранятся в:

```text
/etc/proxy-stack/credentials.env
```

При повторном запуске с теми же доменами установщик использует прежние секреты,
UUID, путь и идентификатор подписки. Fingerprint хранится в том же файле в поле
`VLESS_TLS_FINGERPRINT`. Для старого состояния без этого поля повторная установка
выбирает `edge`; уже явно сохранённое значение сохраняется. Попытка заменить
домены будет остановлена до выключения действующих служб.

Полная повторная установка переводит старый C Teleproxy на MTG, не меняя
MTProto-секреты. Конфигурация MTG всегда заново формируется из действующего
состояния, поэтому ключ в службе и в клиентских доступах не расходится.
Наш прежний временный MTG drop-in сохраняется в резервной копии и заменяется
обычным управляемым unit-файлом.

На новом чистом VPS без перенесённого состояния генерируются новые ключи.
Совместимость MTG с прежним MTProto-секретом сама по себе не переносит доступы
между серверами и не меняет старые IP-адреса в клиентах.

Перед изменением конфигурации создаётся каталог резервной копии:

```text
/root/proxy-stack-backup-YYYYMMDD-HHMMSS
```

## Обновление существующего сервера

Для обновления бинарников без пересоздания конфигураций используйте отдельную
команду **на том VPS, который нужно обновить**:

```bash
cd proxy-stack-installer
git pull --ff-only
sudo bash upgrade-proxy-stack.sh
```

Обновлятор использует версии и SHA-256 из `install-proxy-stack.sh`. Сначала он
собирает MTProxy и Telegram WEB Proxy и проверяет новый Xray, пока прежние службы
продолжают работать. Если сервер уже использует MTG, также подготавливается и
проверяется его бинарник. После проверки выполняется короткое переключение
затронутых служб. nginx и Dante не переустанавливаются.

Обновление бинарников **не мигрирует** старый C Teleproxy на MTG и не меняет
fingerprint, подписку или ручные профили. Оно определяет фактический движок по
службе и метаданным. Для MTG в резервную копию и проверки целостности включаются
оба используемых конфига, unit-файлы и drop-in-настройки. Конфликт метаданных
с действующими службами останавливает обновление.

Секреты MTProto/SOCKS5, VLESS UUID, WebSocket-путь, URL подписки, SSH-ключи,
сертификаты, порты и файлы конфигураций не перезаписываются. Обновление останавливается,
если исходное состояние некорректно или во время сборки изменились защищённые файлы.
Тесты после переключения проверяют Web Proxy, VLESS на обоих портах и SOCKS5.
При ошибке автоматически возвращаются прежние бинарники и маркеры сборки;
резервная копия остаётся в `/root/proxy-stack-upgrade-XXXXXXXX`.

Прервать сборку до переключения можно без простоя. После переключения не завершайте
процесс через `kill -9`: это не позволяет выполнить автоматический откат.
Новые версии Go применяются через пересборку WEB Proxy; сменить только toolchain
недостаточно. Версия Go включена в проверку актуальности установленной сборки.

Зафиксировано 10 ноября 2026 года: Xray `26.11.9`, MTG `2.3.0`, Go
`1.26.10`, MTProxy `69f2f083b57b`, WEB Proxy `c8adb8b7c6b7`.
Системные пакеты nginx, Dante, OpenSSL и certbot обновляются отдельно через APT.

## Восстановление файла доступов

Если `/root/proxy-credentials.txt` был случайно удалён, восстановите его без
переустановки сервисов:

```bash
cd proxy-stack-installer
sudo bash rebuild-proxy-credentials.sh
```

На сервере, установленном через `install-proxy-stack.sh`, утилита читает
`/etc/proxy-stack/credentials.env` и сохраняет действующие MTProto-секреты,
SOCKS5-пароль, VLESS UUID, WebSocket-путь и идентификатор Happ-подписки. По
умолчанию она ничего не ротирует и не перезапускает.

Утилита сохраняет также TLS fingerprint: использует `VLESS_TLS_FINGERPRINT` из
состояния, а для старого состояния без поля — параметр единственной выбранной
активной подписки. При конфликте или неоднозначности она останавливается,
не создавая файл с выдуманными доступами. На ручной установке выводятся точные
активные URI; отсутствующие IP- и резервные профили не синтезируются.

Показать восстановленный файл сразу после создания:

```bash
sudo bash rebuild-proxy-credentials.sh --print
```

Для старой или вручную собранной конфигурации, у которой нет постоянного файла
состояния, укажите домены:

```bash
sudo bash rebuild-proxy-credentials.sh \
  --domain d1.example.com \
  --ipv6-domain d2.example.com
```

Если в `/var/www/faketls/happ` осталось несколько файлов подписок, утилита не
объединяет их автоматически. Укажите идентификатор единственной рабочей
подписки — имя файла без `.txt`:

```bash
sudo bash rebuild-proxy-credentials.sh \
  --domain d1.example.com \
  --subscription-id 0123456789abcdef0123456789abcdef
```

На старом сервере SOCKS5-пароль можно сохранить только при наличии прежнего
`/root/proxy-credentials.txt`. Если открытый пароль утрачен, его невозможно
получить из `/etc/shadow`; выполните явную ротацию:

```bash
sudo bash rebuild-proxy-credentials.sh \
  --domain d1.example.com \
  --rotate-socks-password
```

После ротации обновите SOCKS5-пароль во всех клиентах. Новый пароль будет
записан в `/root/proxy-credentials.txt`, а на установке, управляемой этим
проектом, также в `/etc/proxy-stack/credentials.env`.

## Основные файлы на сервере

| Файл | Назначение |
|---|---|
| `/root/proxy-credentials.txt` | Клиентские конфигурации и секреты |
| `/etc/proxy-stack/credentials.env` | Постоянное состояние установщика |
| `rebuild-proxy-credentials.sh` | Безопасное пересоздание файла клиентских доступов |
| `/etc/proxy-stack/frontend.env` | Движок FakeTLS, пути служб и сохранённый TLS fingerprint |
| `/etc/mtproxy/mtg.toml` | Закрытый конфиг MTProto FakeTLS IPv4 |
| `/etc/mtproxy/mtg-ipv6.toml` | Закрытый конфиг MTProto FakeTLS IPv6, только при втором домене |
| `/etc/tproxy-server/config.json` | Настройки Telegram WEB Proxy relay |
| `/etc/tproxy-server/profiles.json` | Закрытый WEB-профиль и секрет |
| `/etc/danted.conf` | Настройки SOCKS5 |
| `/usr/local/etc/xray/config.json` | Настройки VLESS/Xray |
| `/etc/nginx/sites-available/proxy-stack.conf` | HTTP, TLS и WebSocket reverse proxy |

## Диагностика

Состояние служб:

```bash
systemctl status teleproxy tproxy-server mtproxy danted xray nginx
```

Если включён IPv6:

```bash
systemctl status teleproxy-ipv6 mtproxy-ipv6
```

Последние сообщения журналов:

```bash
journalctl -u teleproxy -u tproxy-server -u mtproxy -u danted -u xray -u nginx --no-pager -n 150
```

Открытые порты:

```bash
ss -lntp
```

Проверка конфигураций:

```bash
nginx -t
/usr/local/bin/xray run -test -config /usr/local/etc/xray/config.json
/usr/sbin/danted -V -f /etc/danted.conf
curl --fail http://127.0.0.1:8081/readyz
/usr/local/bin/mtg doctor /etc/mtproxy/mtg.toml
curl --fail http://127.0.0.1:8888/stats
```

Для второго домена дополнительно проверьте `mtg doctor /etc/mtproxy/mtg-ipv6.toml`
и статистику `http://127.0.0.1:8890/stats`. `doctor` проверяет домен, время,
сертификат nginx и связь с Telegram до запуска службы. При установке его
диагностика сохраняется в закрытых `/etc/proxy-stack/mtg-doctor-*.log`.

Установочные проверки выполняются на самом VPS и не доказывают доступность
маршрута из сети клиента. После импорта проверьте открытие сайтов и отправку
сообщений, а не только показанный приложением пинг.

Таймер обновления Telegram relay-конфигурации:

```bash
systemctl list-timers mtproxy-config-refresh.timer
```

## Безопасность

- SOCKS5 требует логин и пароль, но сам протокол не шифрует соединение до VPS.
- VLESS доступен через TLS с сертификатом Let's Encrypt.
- Xray слушает только `127.0.0.1`; наружу VLESS публикуется через MTG/nginx
  на `443` и напрямую через nginx на резервном `9443`.
- Telegram WEB Proxy relay и его административный endpoint слушают только loopback; TLS обслуживает существующий nginx.
- Случайные секреты, UUID и WebSocket-путь создаются индивидуально при установке.
- MTG работает от отдельного пользователя `mtg` с единственной capability
  `CAP_NET_BIND_SERVICE`. EE-секрет читается через systemd `LoadCredential`,
  а не из аргументов процесса или переменных окружения. Конфиги MTG имеют права `0600`.
- Не публикуйте `/root/proxy-credentials.txt`, `/etc/proxy-stack/credentials.env`
  и `/etc/mtproxy/mtg*.toml`. Резервные копии тоже содержат секреты.
- MTG не перезапускается при продлении сертификата nginx или обновлении
  relay-конфигурации legacy MTProxy: эти файлы он не читает.
- Регулярно обновляйте систему и следите за журналами необычных подключений.

## Поддерживаемый сценарий

Проект предназначен для нового VPS. Если нужные порты заняты сторонними службами, установщик завершится без попытки их удалить или перенастроить.

## Проверка установщика перед публикацией

```bash
for script_path in install-proxy-stack.sh upgrade-proxy-stack.sh rebuild-proxy-credentials.sh tests/*.sh; do
  bash -n "$script_path"
done
for test_script in tests/test-*.sh; do
  bash "$test_script"
done
```

Регрессионные тесты используют только временные файлы и заглушки: без root,
перезапуска служб и доступа к рабочим серверам. Покрываются IPv4/IPv6-генерация,
секреты и права MTG, Edge-профили обоих портов, повторная установка, выбор
действующего движка, сохранение доступов и откат обновления.

Версии сторонних компонентов и их контрольные суммы закреплены непосредственно в начале скрипта.
